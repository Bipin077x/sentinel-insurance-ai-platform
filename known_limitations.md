# AI Insurance Platform POC — Known Limitations & Pre-Production Requirements
This document captures every open item, unresolved governance decision, and structural gap identified across Phases 1.5–11 of the POC build. It is the authoritative handoff artifact from the POC phase. Nothing in this document is a code defect in the current build — these are explicitly scoped-out items that were left unresolved by design, or blocked by environment constraints, during POC development.

## Item 1 — Raw Document Retention Period (Governance, unresolved; Mechanism complete)
Current state: Deletion mechanism built and verified (`core/retention_prune.py`). `raw_documents` can be pruned without affecting `decisions`/`audit_trails` integrity. The retention policy is now configurable via a versioned `config/retention.json` file. The remaining gap is exclusively the legal/governance question of WHAT retention period to configure, not whether deletion is technically safe to perform.

Required before production:
- Legal and compliance review to set jurisdiction-specific retention periods.

## Item 2 — Fairness Evaluation: Synthetic Demographics & Maximal-Signal Testing Only (Governance + Methodology, unresolved)
Current state: `underwriting/fairness_eval.py` and the generated fairness reports evaluate approval-rate parity across synthetic `demographic_group` labels (Group A, Group B) that are directly embedded in the test fixture JSON — not inferred from any real population signal.

The gap has three distinct layers:
- **Layer 1 — Data sourcing (Unresolved).** In production, demographic attributes are almost never directly observed. They must be inferred (e.g. via BISG for race/ethnicity), or sourced through legally validated self-identification methods. The POC still uses synthetic, directly-labeled demographic fields (`Group A`, `Group B`).
- **Layer 2a — Test signal design & Reporting Harness (Resolved in Phase 16).** The evaluation math (`four_fifths_eval.py`) correctly detects disparate impact when population skew interacts with an existing hard, binary threshold rule (e.g. `trip_cost >= 5000` causing an automatic referral). This validated the reporting harness, but not the pipeline's vulnerability to complex, interacting variables.
- **Layer 2b — Genuine Continuous Emergent-Bias Detection (Resolved in Phase 16b).** The evaluation framework now supports generating continuous distributional shifts across variables (e.g. `age ~ N(μ, σ)`). However, a literal audit of `risk_scoring.py` and `referral_score.py` confirms that the current architecture uses discrete threshold-based tiers with no continuous multi-factor blending (the only continuous output, `suggested_premium`, is ignored by the decision logic). As a structural consequence, genuine emergent bias from continuous factor interaction cannot arise in this specific implementation — bias, when present, will always be traceable to a specific threshold crossing (as demonstrated in Phase 16), which is actually a more auditable failure mode than diffuse blended-weight bias would be. If `risk_scoring.py` is ever redesigned to use continuous weighted combination (e.g., for real actuarial modeling), this Phase 16b harness is ready to re-test it for interaction effects at that time.

Required before production:
- Legal sign-off on demographic sourcing methodology (BISG, self-ID, or other)
- Replacement of synthetic demographic labels with a validated inference method
- Selection of the operative fairness criterion (demographic parity vs. equalized odds vs. calibration) with documented justification — these are mutually exclusive in most real distributions
- Independent third-party audit of the fairness evaluation before any live deployment, required by most emerging AI governance frameworks (EU AI Act Art. 9, proposed NIST AI RMF insurance-sector guidance)

The report generated by Phase 8 carries a mandatory CAUTION disclaimer for exactly this reason. It must not be submitted to regulators as evidence of fairness compliance.

## Item 3 — Integration Adapter Layer: Reference Contract, Not Vendor-Validated (Structural, partially built)
Current state: Phase 17 built `integrations/realistic_adapter.py`, tested end-to-end against a local FastAPI mock (`realistic_mock_server.py`) simulating a REALISTIC generic legacy insurance API contract. The mechanics are now proven against complex failure modes common to legacy cores, including:
- SOAP-style XML payload parsing and serialization
- Idempotency key handling (caching/preventing double writes)
- `CorrelationId` propagation mapping back to `decision_id`
- Eventual consistency (async polling of `202 Accepted` status to `CONFIRMED`)
- Explicit partial-failure handling (logging subsystem split states without retrying the succeeded half)

The gap: This proves the adapter mechanics against a deeply realistic structural model of legacy enterprise APIs. However, the remaining gap is unchanged and explicit: zero validation against any actual named vendor's real API contract (Guidewire PolicyCenter, Duck Creek, etc.). No real vendor documentation was used to build this generic contract.

Required before production:
- API contract review for each real target system
- Adapter implementations rewritten against actual vendor API specs (authentication, payload schema, error semantics will all differ from the mock)
- Integration-layer audit logging (separate from the decision audit trail)
- End-to-end integration tests against staging instances of target systems
- Latency and throughput benchmarking against real network conditions — the mock-based Phase 11 benchmarks (see Item 5 below) do not reflect real integration latency

## Item 4 — The 19 Legacy ⚠ legacy-text-match Records (Structural, permanent)
Current state: The escalation report marks 19 historical decisions as `⚠ legacy-text-match` — meaning their escalation mechanism was inferred from `reasoning_text` pattern-matching rather than the structured `override_reason` field introduced in Phase 8.

Why these cannot be fixed: The WORM append-only constraint (SQLite triggers blocking UPDATE on `decisions` and `audit_trails`) is working as designed. Retroactively populating `override_reason` for existing records would require an UPDATE, which the system correctly refuses. The `⚠` marks are therefore permanent and correct — they accurately reflect the evidentiary basis of those decisions at the time they were made.

Implication for production: Any future compliance review of decisions made before the Phase 8 structured-field fix will see these warnings. This is the right behavior. For a production system, the fix is to ensure `override_reason` is set on all decisions going forward — which the updated pipeline runners now do.

## Item 5 — LLM Model Pinning: Mock vs. Real (Structural, POC-scoped)
Current state: The model registry (`core/model_registry.py`) pins `mock-llm-1.0-0613` as the active model. All LLM responses are deterministic mocks. The calibration system (semantic entropy across 5 samples) is exercised structurally but produces artificially high confidence because the mock always returns the same output for a given input.

Downstream consequence, confirmed across the build: because the mock is deterministic, the escalation rates observed throughout Phases 2–5 (e.g., claims settling at 83.3% auto-decided, underwriting/brokerage at effectively 100% accuracy) are artifacts of the mock's determinism and are not representative of expected production behavior. A real, non-deterministic model will produce genuine sampling variance that the mock structurally cannot — meaning real deployment should be expected to see MORE calibration- triggered escalations, not fewer, than anything observed in this POC. The deterministic overrides (`fraud_score`, `referral_score`, hard ceilings) become more load-bearing in production, not less, since they are the only mechanisms in this design proven to catch confidently-wrong output regardless of model determinism.

Required before production:
- Replace mock LLM client with a production LLM endpoint with: Version pinning (model version logged to `model_changelog` table)
- Fallback handling for API unavailability
- Rate limiting and cost controls
- Re-run calibration characterization on real model outputs — the confidence thresholds in the escalation policy (0.85, 0.95) were set for mock behavior and will require empirical recalibration against a real model's variance
- Regression test all adversarial tests against the real model before deploying

## Item 6 — Financial Audit Function: Orchestration Verified, Semantic Discrimination Unverified (Structural, POC-scoped)
Current state: Phase 5 built statistical anomaly detection (`audit/anomaly_detection.py`, deterministic z-score/IQR-based outlier detection) and an LLM-assisted review stage (`audit/llm_review.py`) wrapped in the same faithfulness and calibration scaffolding used everywhere else in the system. The end-to-end orchestration was verified: a statistically flagged record (e.g., a claim with Z-score 4.51 against a threshold of 3.0) correctly flows through to an LLM review verdict (`dismiss_benign`), which is correctly logged through the append-only path.

The gap: The mock LLM's review logic in `_mock_audit_llm` routes its response based on a literal string match — "LEGIT" in `subject_id` — not on any semantic evaluation of the claim's actual content. This means Phase 5 proves the pipeline plumbing is correct (detection → LLM review → faithfulness check → logging), but does not prove the system can actually distinguish a legitimately large claim from a fraudulent one. That capability is entirely unvalidated in this POC.

Required before production:
- Real-LLM validation of the audit-review stage specifically, dependent on the mock→real migration in Item 5
- A labeled evaluation set of true positive (genuine fraud/anomaly) and true negative (benign outlier) cases, built independently of any keyword or string-match shortcut, used to measure actual precision/recall of the audit-review stage
- Until this is done, no output of the audit-review stage should be represented — internally or to a regulator — as evidence of working fraud detection. It should be represented as: "detection and logging infrastructure verified; discrimination capability unvalidated."

## Item 7 — Mixed-Format Document Ingestion: Positive OCR Path Unverified (Environment-blocked)
Current state: `ingestion/document_parser.py`'s native-PDF text extraction path is verified working (confirmed: `native_claim.pdf` parsed with method `native_pdf`, confidence 1.00, correct text extracted). The OCR path (`pytesseract`) could not be exercised in the build environment — the Tesseract binary was unavailable (a Windows `winget` install attempt hung on a UAC/admin prompt in a headless session and could not be completed).

The specific consequence: both a genuinely scanned document (`scanned_claim.png`) and a deliberately garbled/low-quality scan (`garbled_scan.png`) produced the identical error — "Tesseract OCR binary is not available" — rather than two different outcomes (successful extraction vs. quality-gated rejection). This means the quality-gate behavior the spec required (garbled scans routing to review due to low OCR confidence, not due to the binary being missing) is currently indistinguishable from a simple environment failure in the available test output. The garbled-scan routing-to-review result cannot be trusted as evidence the quality gate works as designed.

Required before production:
- Install Tesseract (or an equivalent OCR engine) in a properly provisioned environment with administrative access, or set `pytesseract.pytesseract.tesseract_cmd` explicitly to a portable/ pre-compiled binary that doesn't require an installer
- Re-run BOTH the positive scanned-document case and the garbled-scan case and confirm they now produce genuinely different, correct outcomes: successful structured extraction for the clean scan, and a distinct quality-confidence-based rejection (not a binary-availability error) for the garbled one
- Only after that distinction is demonstrated should the OCR quality gate be considered verified

## Item 8 — Anomaly Detector Redundancy (Methodology, unconfirmed value)
Current state: Phase 12 proved that the statistical `amount_outlier` anomaly detector perfectly overlapped (100% redundancy) with the deterministic rule-based fraud flags on the Kaggle real-world dataset. The 5 cases it flagged were explicitly caught by the deterministic rule (due to presence of "Major Damage").

The gap: This is a useful demonstration of defense-in-depth, but it confirms that the anomaly detector is currently non-additive to rule-based fraud detection on tested data. Its independent value remains unconfirmed.

Required before production:
- Test the anomaly detector on a broader and more diverse dataset to ascertain whether it detects fundamentally new vectors of fraud not captured by deterministic rules.
- If it does not add independent value, reconsider the cost/complexity trade-off of maintaining the secondary infrastructure compared to running solely rule-based flags.

## Item 9 — Fraud Signal Real-World Precision Uncertainty (Methodology, verified bounds)
Current state: Phase 13 conducted 5-fold cross-validation on the Kaggle dataset to validate the deterministic "Major Damage" fraud correlation. The rule was consistently rediscovered in every fold. However, due to the limited sample size (only ~247 total positive fraud labels distributed across folds), precision ranges between ~55–65% and recall between ~35–50%. 

The gap: This is a verified, dataset-wide fraud correlate, but the metrics have meaningful mathematical uncertainty driven strictly by sample size variance. The exact precision point-estimate will fluctuate on similarly small slices.

Required before production:
- Communicate that "Major Damage" is a validated, dataset-wide fraud correlate with expected real-world precision of ~55–65% and recall ~35–50%, not a fixed absolute figure.
- Conduct evaluation on a larger dataset (e.g. 10k+ cases) to tighten the statistical confidence intervals if precise point-estimates are required by stakeholders.

## Item 10 — Underwriting Risk Stratification Divergence (Methodology, structurally verified)
Current state: Phase 18 evaluated the synthetic `risk_scoring.py` algorithm against ~63,000 real-world travel insurance applications (AXA dataset) using 5-fold stratified cross-validation. The test correctly bounded the scope by noting the dataset lacks fraud or accept/decline ground truth.

The gap: The results produced two major findings. First, the synthetic logic (Low vs Medium) produces negligible, fold-unstable separation (Low: 1.46%, Medium: 1.65%, inverting entirely on Folds 2 and 4). Second (the headline finding), the pipeline already has access to fields carrying massive real-world risk signal that it currently ignores: `Duration` shows a 3.7x risk multiplier (0.71% vs 2.62%), and `Agency` (which confounded `Destination` in the data) showed a staggering 6.6% claim rate for a single agency compared to 0.1% for others. Note: The High Tier was mathematically unreachable because the `pre_existing_conditions` field could not be mapped (defaulting to False). This is a coverage limitation of the dataset, not evidence that the High-tier logic itself is flawed.

Required before production:
- Redesign `risk_scoring.py` using real-world actuarial evidence to properly weight massive, existing univariate signals (e.g., `Duration`).
- Investigate the `Agency` confounder as a data-quality or business-segment signal. A 66x difference between agencies likely reflects reporting practices or policy terms, NOT intrinsic trip risk. Do not blindly weight `Agency` into pricing; treat it as an operational metric to normalize.
- Re-run the Phase 18 validation harness on the redesigned model to prove monotonic risk stratification holds consistently across real-data folds.

## What the POC has validated
The following architectural claims are considered verified within the POC's explicitly synthetic, mock-LLM scope:

- WORM-compliant, hash-chained audit trail with cryptographic verification, including verification across records added after a human review override
- Escalation gate with structured mechanism field (`fraud_override`, `referral_override`, `amount_ceiling`, `extraction_validation_failure`)
- Faithfulness verification (fabrication detection via cited-rule cross-check, plus outcome/reasoning coherence checking)
- Semantic entropy calibration as a gate signal (structurally verified; see Item 5 for the limits of this verification against a deterministic mock)
- Regulatory reporting layer with non-repudiation (SHA-256 hash logged per report, live integrity check on every Case Audit Report)
- Redaction pipeline (PII removed before snapshot; raw text under separate short-lived retention)
- Compliance ruleset versioning (hash-pinned YAML, manifest verification)
- Prompt versioning (hash-pinned prompts, logged per decision)
- Fairness evaluation framework structure (with explicit methodology limitations documented at every output point — see Item 2)
- Integration adapter round-trip mechanics: real HTTP calls, retry/backoff on failure, confirmed server-side receipt (see Item 3 for vendor-validation status)
- Human-in-the-loop review workflow: override recorded as a new append-only record alongside the original AI-proposed decision, chain integrity confirmed across both
- Native-PDF document ingestion (text-based PDFs only — see Item 7 for OCR status)
- Audit-function orchestration: statistical anomaly detection correctly triggers LLM review, which correctly flows through faithfulness checking and append-only logging (see Item 6 for the limits of what this proves)
- Business-outcome timing/cost instrumentation, structurally correct and explicitly labeled as mock-based, non-representative of production latency/cost, with no fabricated human baseline

These validations hold structurally. They do not constitute a production readiness assessment. Items 1, 2, 3, 5, 6, and 7 are each independently blocking for production deployment.
